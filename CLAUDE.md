# Контекст проекта для Claude

Telegram-бот — помощник продавцов на playerok.com (аналог FunPay Cardinal / Easy Sell),
многопользовательский: каждый продавец подключает свой аккаунт Playerok.
Владелец бота пишет по-русски, с телефона (ПК нет) — отвечать по-русски, коротко,
давать пошаговые инструкции под мобильный интерфейс. Проверять вживую он может только
в Telegram и в Railway; присылает скриншоты.

## Архитектура (bot/)

- `main.py` — запуск: aiogram-поллинг + фоновый поллер Playerok.
- `playerok/` — GraphQL-клиент. `queries.py` — все запросы. Транспорт curl_cffi с
  имитацией Chrome. Клиент сам чинит запросы: убирает неизвестные поля
  («Cannot query field») и правит типы переменных (`T` → `T!`), кэширует исправленное.
  403 с HTML = защита/геоблок, НЕ истёкшая сессия (не разлогинивать!).
  Лимит Playerok ~15 запросов/мин на аккаунт: `_rate_wait` — общий лимит `PLAYEROK_RPM`
  (по умолч. 12/мин на токен) для всех запросов; «Too many requests»/429 → ждать 15/30/45 с и
  повторить. HTTP 500/502/504 на сохранённых (GET) запросах — 2 повтора (3, 8 с); мутации не
  повторяются. В тестах (подменённый транспорт) лимит не действует.
- `services/poller.py` — каждые 30 с: сделки, чаты, лоты → `automation.py`.
- `services/automation.py` — приветствие, автовыдача, автоподтверждение, автоответчик,
  напоминания, тексты после отзывов/проблем, автоподнятие и перевыставление лотов.
- `services/features.py` — реестр функций, шаблоны с переменными `{Имя_Клиента}` и т.п.
- `services/notifications.py` — все уведомления продавцу (9 типов, вкл/выкл, звук).
- Уведомления в стиле Easy Sell: «Новое сообщение от клиента для …», «Новый отзыв для …»,
  «Подтверждение сделки для …»; ник покупателя — ссылка `profile_url` (`/profile/<ник>/products`,
  формат не подтверждён). Кнопки `deal_kb` (keyboards.py), обработчики `cm:*` в `handlers/chat.py`:
  ✉️ Ответ (`reply:`), 📋 Шаблоны (`QuickReply`, переменные как в шаблонах), 💬 Весь чат
  (сохранённый запрос `chatMessages`, 24 последних), ✅ Подтвердить (`updateDeal` SENT) и
  ↩️ Возврат (`updateDeal` ROLLED_BACK, как PlayerokAPI) — оба с вопросом «Точно?»; заказ —
  по deal_id или активный заказ чата из `DealState`. Вживую не проверено.
- `services/pricing.py` + `handlers/pricing.py` — «📉 Снижение цен» (функция `dumping`):
  `PriceRule` (свой лот, ключевые слова конкурентов, шаг ₽, минимум ₽ для покупателя);
  раз в N мин: `item` → категория → `category_items` (items c gameCategoryId) → самая
  низкая чужая цена (тот же способ получения — фильтр obtainingTypeId) − шаг → `updateItem {id, price: rawPrice}` (как PlayerokAPI.update_item;
  input.price = цена продавца, пересчёт по price/rawPrice). Только снижает. Вживую не проверено;
  Конкуренты — по ключевым словам или кнопкой «🏷 По названию моего лота» (competitor_kw="*",
  `name_match`: все числа из названия целым словом; без чисел — половина слов).
  «✂️ Снизить цену своих лотов сейчас» (dp:cut → dp:cutok, FSM `CutPrice`): разово, свои активные
  лоты по словам/названию/ссылке (`select_my_lots`, до 30), затем выбор галочками (`CutPrice.pick`,
  dp:cs:<i>, «Только N ₽» dp:csp:<цена>, dp:csall/csnone, dp:csok; один лот — без выбора); `parse_cut`: просто число = НОВАЯ цена
  («682»), «-10» — на 10 ₽, «-5%» — на 5 % (раньше «682» значило «снизить на 682» — продавец
  чуть не поставил 18 ₽). Предпросмотр и подтверждение, `cut_price` = item → updateItem; только
  вниз и не дешевле половины текущей за раз (`MAX_DROP`). Ошибки Playerok «Minimal price - N» /
  «price must be at least N» — по-русски (`price_error`). Вживую: снижение 700→682 и 684→682
  Playerok отклонил «Minimal discount - » (без числа) — есть минимальная скидка при снижении
  цены, размер неизвестен. Для updateItem/publishItem/updateDeal ошибка пишется в лог целиком,
  а поля из extensions добавляются к тексту (`error_details`) — так узнаем размер.
  Премиум-лоты (`Item.is_premium`, priority=PREMIUM) — цену Playerok менять не даёт (со слов
  продавца): в ✂️ они не предлагаются, `cut_price`/`check_rule` их пропускают, `find_my_lot` по
  названию берёт только обычные. Вживую 684→682 у обычных лотов тоже было «Minimal discount»
  (extensions: только statusCode 400) — порог скидки так и неизвестен.
  неизвестно, уходит ли лот на модерацию после смены цены. «🌐 Выгода по рынку» — кнопка в
  Аналитика → «🧮 Калькулятор прибыли» → экран настроек `_market_menu` (сразу), отчёт — «▶️ Посчитать»
  (dp:nomrun; обработчики dp:nom* в handlers/pricing.py; прогресс в одном
  сообщении, таймаут 300 с, частичный результат при лимите, любая ошибка — сообщением)
  (`nominal_report`): по ссылке на лот — категория+способ получения, до 20 страниц, самый
  дешёвый ЧУЖОЙ лот на каждый номинал (первое число в названии; свои исключены), его цена для
  покупателя ÷ курс (по умолч. 104) − закупка $ по номиналу (`nominal_costs`) → прибыль; 5 страниц.
  Закупка: вручную (`nominal_costs`) или с FazerCards (`nominal_fazer_cat`, только админ, ключ из
  /giftcard; номинал из названия оффера, цена price_usd, видно наличие; FazerCards главнее ручной).
  Трекер (`market_track`, порог `market_track_min` $): в поллере раз в 30 мин `track_market`,
  уведомляет, когда номинал СТАЛ выгодным (прибыль ≥ порога, есть в наличии); без дублей
  (`market_track_seen`). Сканирование Playerok — вне сессии БД.
  Поиск минимума (`market_scan`): по каждому номиналу закупки отдельный запрос `items` с
  filter.searchQuery=«число» и sort {field: price, direction: ASC} (формат sort — как в
  PlayerokAPI для других запросов; для items вживую не подтверждён). Не отсортировано —
  листает выдачу до 8 стр.; поиск не применился (проверка по самому большому номиналу) —
  просмотр каталога до 15 стр. Ошибка на sort/searchQuery — отключаются до перезапуска.
  Раньше брались первые 5 страниц каталога — минимумы были неверные (там сверху не дешёвые).
  «📦 Разделы закупки» (handlers/market.py, mk:*; services/market_sections.py; таблицы
  `CostSection` бренд+страна+lot_ref+kw+fazer_cat, `CostEntry` номинал→$): бренды Apple/PlayStation/
  Xbox/Nintendo/Steam/Roblox, страны кнопками (+своя), номиналы списком «5 4.6», правка/удаление
  кнопками. Активный раздел (★, настройка `market_section`) — по нему отчёт и трекер
  (`pricing.market_setup`); без раздела — старая схема (nominal_costs + общий лот). Старый список
  при первом открытии переезжает в «Roblox · Без страны». Для подарочных карт номинал — число у
  валюты («5$», «100 TL», `nominal_cur(currency_first)` → номинал+валюта). Страна лота —
  `country_verdict`: слова своей страны → да, слова другой страны → нет, иначе по валюте
  номинала (COUNTRIES[...][2]: «10 TRY» для США — нет); лоты другой страны не берутся никогда,
  без страны и валюты — только если своих нет (строка помечена); `kw` «-» — не проверять.
  Вживую в разделе США бот взял «Apple 10 TRY Турция»: первая страница поиска «10» (24 самых
  дешёвых) — сплошь турецкие → теперь при фильтре страны листается до 6 страниц.
  Лот для сравнения раздела не обязателен: `auto_lot_ref` берёт его из раздела того же бренда
  или из своих активных лотов со словом бренда (`BRAND_WORDS`), иначе просит ссылку один раз.
  Трекер: интервал проверяется ДО запросов к FazerCards/Playerok.
- `services/analytics.py`, `services/history.py` — аналитика и импорт истории продаж.
  Калькулятор прибыли (Аналитика → «🧮»): `ProfitRule` (слово + чистая прибыль с 1 продажи в
  `cost`, валюта `currency`, по умолчанию $); продано шт за 1/7/30 дней × прибыль. Комиссии нет.
- `handlers/` — экраны бота (settings = автоматизация, account = профиль, stats, admin).
- `plugins/` — платные плагины. `access.py` — выдача доступа (`/grant`, `/revoke`,
  `/access`, `/sellers`). `plugins/stars/` — звёзды через Fragment за USDT (TON).
- `db.py` — модели; `_add_missing_columns` досоздаёт новые колонки в старой базе.
- `plugins/giftcard/` — Gift Card через FazerCards (api.fzr.cards, OpenAPI:
  `/public/docs/openapi.json`). Закрытый: только для `is_admin` (покупки с баланса владельца),
  команда `/giftcard`. Ключ вводится в боте («🔑 Ввести API-ключ», шифруется SECRET_KEY,
  настройка `giftcard_api_key_enc`), запасной вариант — переменная `FAZER_API_KEY`. `client.py` — только HTTP
  (balance, giftcards, giftcards/cards, giftcards/order с `Idempotency-Key`, orders/{id});
  `service.py` — состояния `GiftcardOrder` (PROCESSING→AWAITING→BOUGHT→DELIVERED; UNKNOWN,
  FAILED, NEEDS_CHECK). Строка заказа пишется до покупки; повтор при неизвестном итоге —
  только с тем же ключом (`playerok-<tg>-<deal>`). Подключён в `_process_deal` перед
  автовыдачей; после выдачи `state.delivered=True` → обычное автоподтверждение.
  Формат `order.cards` в документации не описан: строки или поля code/pin/serial…,
  иначе NEEDS_CHECK. Вживую не проверен.

## Логи

`bot/logs.py`: файл `/app/data/logs/bot.log` (ротация 1 МБ × 3). Команда `/logs` в боте
присылает файл: владельцу — все строки, продавцу — только помеченные `[tg=<его id>]`.
Строки продавца помечать через `tag(tg)`. Не писать в лог токены, seed, cookies,
выдаваемые товары и переписку. Перевыставление пишет причину пропуска каждой сделки
(один раз) — первым делом просить у владельца `/logs`, если что-то «не работает».

## Что НЕ проверено / открытые задачи

- Лоты/перевыставление/поднятие переделаны по рабочей библиотеке PlayerokAPI и боту
  Playerok Universal (github.com/alleexxeeyy, raw.githubusercontent.com доступен из облака;
  сам playerok.com из облака — 403 DDoS-Guard geoblock). Ключевое:
  `items`, `item`, `itemPriorityStatuses` — только сохранённые запросы (GET /graphql,
  `extensions.persistedQuery.sha256Hash`, хеши в `client.PERSISTED_QUERIES`); на текст
  запроса `items` сайт отвечал «Access denied». Перевыставление после продажи: свой лот
  со статусом SOLD ищется по названию (`find_sold_item`) — ID лота в сделке не тот
  (republish по нему → 404); затем `item` (rawPrice, priority, mayBePublished) → тарифы по
  int(rawPrice) → publishItem {itemId, priorityStatuses:[id], transactionProviderId:LOCAL}.
  PREMIUM-лот — только премиум-статусом (платно, при «Платное восстановление»);
  mayBePublished=false — Playerok не даёт выставить повторно. Поднятие = PREMIUM-статус
  через increaseItemPriorityStatus (+transactionProviderData), цена от Playerok, лимит/сутки.
  Если хеш устареет — ошибка «сохранённый запрос … устарел»: взять новый из misc.py PlayerokAPI.
  Вживую после этой правки ещё не проверено.
- Автоподтверждение (`updateDeal` → `SENT`): вживую Playerok ответил 500 «Something gone wrong»
  (запрос тот же, что в PlayerokAPI и exfador/playerok-api; exfador после ошибки перечитывает
  сделку — статус мог смениться). Теперь: до 3 попыток не чаще раза в минуту
  (`DealState.confirm_tries/confirm_tried_at`), свежий статус — из опроса; SENT после неудачной
  попытки = успех автоподтверждения; продавцу — одно сообщение после 3-й неудачи.
  Перевыставление после продажи вживую СРАБОТАЛО («Выставил заново … Открыть лот»). После автовыдачи заказ отмечается выполненным
  автоматически (флаг `autodelivery_confirm`, по умолчанию вкл., переключатель в экране
  Автовыдачи), даже если функция «Автоподтверждение» выключена.
- Массовое перевыставление по списку лотов (все SOLD/EXPIRED раз в интервал) УДАЛЕНО: когда
  список заработал, бот выставил продажи полугодовой давности. Выставление — только сразу после
  новой продажи и вручную. Кнопка «🧹 Снять лоты, выставленные ботом за 24 ч» (rl:undo) снимает
  их через REST /item/{id}/discontinue (по ActionLog kind=relist, target = ID выставленного лота).
- Экран «Автовыставление» показывает продажи за 48 ч и судьбу лота (✅/❌/⏳/⏸ с
  причиной) по `DealState.item_id/item_url/relist_note`, без запроса к Playerok; кнопка
  «🔄» (rl:pub) ищет проданный лот по названию.
- `markChatAsRead`, отзыв внутри сделки (поля `review` у ItemDeal нет) — запросы
  написаны вслепую.
- Плагин звёзд (Fragment) целиком не проверен: нужны cookies fragment.com, seed отдельного
  кошелька, «🔎 Проверить», затем пробный заказ на 50 звёзд. Методы Fragment — в
  `plugins/stars/fragment.py` (`METHODS`).
- У владельца в запасе автовыдачи могут лежать уже выданные коды (после старого отката
  базы) — напомнить сверить и удалить.

## Автовыдача — как сопоставляется лот

Запас ищется по названию лота без учёта регистра, эмодзи, знаков и лишних пробелов
(`norm_lot`), с запасным совпадением по целым словам (`match_stock_key`). Выдача
повторяется на каждом опросе, пока заказ PAID и не выдан, но только для заказов не старше
24 ч (старые продавец мог закрыть вручную).

## Принятые решения (не пересматривать без причины)

- Не показывать владельцу балансы, токены, seed-фразы и переписки других продавцов —
  ни поштучно, ни в `/sellers`. Допустима только обезличенная сводка числами.
- Seed-фразы и cookies хранятся зашифрованными, сообщения с ними бот удаляет.
- «Вечный онлайн» не делали: неизвестно, как Playerok определяет онлайн.
